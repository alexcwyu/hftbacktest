Purpose and scope

Rust/Python high-frequency market replay with separate exchange/local processors, configurable latency/queue/fee models and a shared Bot interface for live connector deployment.

Design decisions

Decision Rationale Tradeoff Evidence
Separate exchange-time and local-time processors. Scheduler represents feed and order delays using distinct event streams. Results depend on latency/queue/feed calibration. build (L254) / goto (L755) / ConstantLatency (L28)
Share Bot API between replay and live mode. Strategy-facing order/time operations can target either implementation. Remote execution is via connector integration and has different operational prerequisites. Bot (L784) / LiveBot (L195)

Replay order with modeled latency

Events are selected by earliest timestamp, so local/exchange feed and order messages can interleave. This diagram records dispatch possibilities, not a universal strict local-then-exchange event ordering.

Strengths and limits

Strengths

  • Models explicitly expose entry/response latency and order queue position behavior. ConstantLatency (L28) / RiskAdverseQueueModel (L44)

Limitations

  • NoPartialFillExchange fully fills taker quantity at the best regardless of displayed liquidity; large orders can be unrealistic. NoPartialFillExchange (L64)
  • Original missing replay archive remains a documented failure even though maintenance completion excludes it; SDK fixtures and native success are not substitute replay proof. docs/validation.md (L16)
  • Inline no-partial model support summary is outdated; capability evidence uses actual ack_new branches rather than the comment. ack_new (L314) / NoPartialFillExchange (L64)

Validation scope

The linked validation and command records preserve actual historical runs and user-authorized exclusions. This source/document review does not rerun application tests, establish live trading readiness or rank benchmark performance. Current data, credential and runtime prerequisites remain material.
